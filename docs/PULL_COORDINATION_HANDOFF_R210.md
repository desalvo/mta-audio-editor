## Supported topology and transaction contract

One Linux MTA authority owns one local SQLite ledger, task inputs/results and its normal project/publication/billing stores. Several HTTP processes may share that authority only in the same pinned host/storage/PID namespace. Remote nodes use verified private HTTPS; they never open SQLite, mount project storage or publish project files. The authority assigns each task once and performs economic settlement/publication through the existing owners. No NFS/SMB-mounted SQLite, load balancing over independent databases, multi-leader database, automatic authority failover or HA certification is supported.

`app/ai_pull_coordinator.py` stores node hashes, admission state/generation, task plan/source/rights/owner, a single worker instance+nonce, frozen result and completion proof, original HTTP request mapping and operator audit. Source and reserved result capacity are bounded. Assignment is a `BEGIN IMMEDIATE` compare-and-set; one node has at most one dispatched task and a job has one task. A new instance cannot take an uncertain task. There is no lease-expiry takeover. All mutation paths recheck original claim/fence/current epoch; historical closed proofs retain their existing exact-retry rules.

Direct ledger creation invokes a private transaction hook: quota reservation, license snapshot, worker owner and task storage either all commit or all roll back. Deferred generation admission is also recorded inside its stable ledger transaction. An intent admitted before a drain may finish; a new intent during drain cannot leave a partial economic job. A legacy/local owner without a pull admission cannot be silently adopted. Account billing disabled does not strip ownership from pull generations. Free-only decisions freeze `billable=0`, a license exemption and no resource charge contract; real measured CPU remains accounting evidence. These fixes also preserve free-only provisional ledger semantics for local generation. Actual generation admission uses the authoritative model permission context, not a user-supplied exemption.

Known worker results freeze before economic delivery. Direct success/failure and known failed/cancelled deferred work use `finish_job_idempotent` with the original owner; successful deferred work waits for the existing publication/billing outboxes. Original API request fingerprints/keys bind to the task atomically. Completion records the request outcome and durable result so `/request-status` and `/request-result` recover after the original HTTP process disappears, without a second inference or requiring the optional filesystem cache. Concurrent retries are exact and idempotent. Conflicting receipts, request bindings, epochs, outputs or usage stay blocked.

## Worker and failure boundaries

`app/ai_pull_worker.py` only runs operator-selected registered executables with the existing `--request`/`--output` protocol. It validates the plan, source hash and its own current model policy against the admitted decision, stages private source files itself, measures the actual child with `wait4` and validates bounded WAV/artifact ZIP output. API users cannot select commands or filesystem paths. Observed/unverifiable descendants prevent completion and leave the original assignment held. GPU/energy/full remote-kernel instrumentation is not implemented or self-certified; only verified available direct-child CPU evidence is delivered.

The owner-only, fsynced journal has requesting/claimed/dispatched/ready/done phases. The dispatched barrier precedes `Popen`; restarting that phase exits 78 and never reruns inference. Source is removed from the journal at dispatch. Ready results can retry only completion. An exact job acknowledgement clears private result/nonce data; a malformed 200 cannot. A lost completion response after authorized account erasure can clear the node's private result using a server-keyed opaque receipt, without recreating the user's ledger. That receipt retains no raw owner, job ID, source, result or nonce and expires after 90 days.

`WorkerClient` validates a fixed HTTPS origin, uses system/operator CA verification before credentials, never follows redirects or proxy environment settings and permits only claim/heartbeat/complete paths. Journal binding includes origin, credential hash and TLS trust material. Changing those values requires review; it cannot silently resume a different authority's job. Revocation never releases a running claim. The optional systemd template stops automatic restart after exit 78; it is not installed/enabled by this package.

The authority is pinned to the boot, local data-directory identity and PID namespace. A copied/relocated database cannot silently become another accepting authority. Process restart on the same authority is supported. A planned reboot/move requires stopping the original authority, draining/settling all tracked work and revoking all nodes before using the explicit closed-only offline rebind procedure. Unknown work forbids rebinding. The procedure keeps admission paused and never certifies physical quiescence. An unexpected reboot with uncertain workers remains held pending the separately required recovery work; there is no unsafe force flag.
