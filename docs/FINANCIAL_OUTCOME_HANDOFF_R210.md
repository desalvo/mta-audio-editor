## Stripe failed-attempt recovery — completed eligible workflow

Previously canceled, zero-received/capturable intents were rejected whenever any charge attempt existed, even when all attempts were definitively failed with no money movement. app/stripe_failed_charge_proof.py now permits a conservative authenticated subset through the existing owner/admin verification actions. The complete workflow is local pending checkout → confirmed provider GET verification → bounded canonical failed-attempt proof → atomic immutable terminal receipt/ledger/fence closure → removal of the existing resume URL → new-purchase admission. Verification never creates an order, cancels a provider intent/session, captures money or issues a refund.

The session must still match its original local owner, price, currency, metadata and original reference and be unpaid/expired or complete. Its intent must already be canceled with exact integer zero amount_received and amount_capturable. Every discovered charge must have the original intent/amount/currency and test/live mode, failed status, strictly false paid/captured/refunded/disputed flags, exact integer zero captured/refunded amounts and explicit null balance/failure-balance transactions. Missing values are not zero. Nonempty history requires a matching latest_charge and explicit matching intent environment. Captured/authorized/refunded/disputed/monetary or ambiguous histories remain blocked, even if other fields claim failure. The implementation deliberately does not generalize to every Stripe failure or reversal shape.

Discovery uses at most 100 charge attempts; truncation, repeated IDs/cursors, malformed pages or overflow block closure. Every charge is read individually; its safe financial snapshot must match the list. The entire collection and intent are reread before final session verification and existing immutable local owner/configuration/epoch checks. Order/capture/key/epoch drift, missing references, 404, timeout, active authorization or any contradictory event cannot clear a checkout. Older empty-history receipt formats are preserved without a forced migration.

The safe sorted proof enters the existing immutable financial event JSON and terminal receipt digest in the same write transaction as intent/charge ownership bindings, zero position, original fence closure and local cancelled status. No new accounting table or wallet credit is created. No card/customer/billing details, client secret or decline message is stored in the proof. Readiness audits validate the proof schema, original order amount and every charge/intent binding; drift or corrupt imported data blocks integrity. An authenticated later paid event remains durable pending for operator review instead of overwriting the empty terminal result. Signed asynchronous failure is resolved only after canonical proof, not by the failure notification alone.

The owner UI is the existing actual /account/credits history and explicit Verify status without collecting payment action; the administrator uses the existing authenticated reconcile-payment action. Both share the same proof service and original ACL/request-integrity checks. Browser acceptance confirms dismissed confirmation causes no verification, successful proof changes history to Cancelled and enables a fresh legitimate purchase, while invalid proof retains the hold across reload. The new-purchase redirect is intercepted in tests; no provider is contacted.

Official technical references consulted 2026-10-23: https://docs.stripe.com/api/charges/object, https://docs.stripe.com/api/charges/list, https://docs.stripe.com/api/payment_intents/object and https://docs.stripe.com/api/payment_intents/cancel. The strict acceptance predicate is an application safety policy, not a claim that every failed charge has this exact shape. No external cancellation API was added or called. An isolated merchant sandbox remains required to validate real object variants and full lifecycle.
