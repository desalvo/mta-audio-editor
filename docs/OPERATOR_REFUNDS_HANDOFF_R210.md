## Functional workflow completed

1. Administrator first reconciles the original payment. The new refund panel on /admin lists locally reconciled refundable Stripe credit payments and PayPal captures. Multiple PayPal captures remain separate choices. Targets are diagnostic candidates, never permission to dispatch. The bounded candidate list currently shows the first 200 funded unrefunded positions; preparation API can address any exact reconciled local order/target. Refund history has paginated administrator and private owner endpoints.
2. Preparation validates exact request fields, positive integer EUR cents, documented reason and an active administrator. It refreshes authenticated canonical provider history through the existing reconciliation service before reserving money. Under BEGIN IMMEDIATE it binds the owner, original order, exact intent/capture, gross/refunded amounts, merchant configuration and source identity to an immutable quote. Over-refunds, unknown targets, pending evidence/disputes, inconsistent local balances or an existing unresolved refund for that order are blocked. A durable regime checkout-kind operation fence is admitted; preparation never calls the refund POST.
3. A separate explicit confirmation dispatches the prepared quote. Current merchant/payment identity is checked before provider readback; balances and active admin authorization are checked again under the dispatch transaction. A changed quote requires cancellation and a new preparation. Only prepared records can dispatch. The transaction commits uncertain state before any irreversible I/O. Stripe receives a fixed-host POST /v1/refunds with the bound PaymentIntent, exact cents and mta_refund metadata; PayPal receives the bound capture /refund with exact EUR amount and custom_id. The stable provider request key is secondary defense; no path ever automatically reposts, even if a provider forgets its idempotency key or the process restarts.
4. An authenticated POST response can retain the candidate refund ID, including a minimal PayPal response, but cannot settle accounting. GET-only verification retrieves that exact refund resource using the original merchant configuration and requires exact ID, operation metadata/custom_id, original target, EUR amount and a known provider status. Wrong/unknown objects, 404, malformed responses, HTTP failures, timeout and process death leave the operation open. A provider pending/requires-action result remains pending. A caller-supplied reference is only a hint; it does not grant settlement.
5. A completed or definitive failed/cancelled provider refund still requires fresh canonical provider history reconciliation. Only the existing authenticated ledger service mutates credits/refund/receivable records, transactionally. Successful refunds must be reflected in cumulative canonical balances; PayPal also requires the exact local refund ID/capture/amount entry. Immutable source identity is rechecked before this write path and after reconciliation. Only then does the refund journal reach settled or verified failed and close its own operation fence. Ledger readback/commit failures keep pending status and the known ID for GET-only retry. Cancellation only cancels a prepared record; it can never negate an attempted provider mutation.

## Actual local economic behavior and durability

Stripe full/partial credit refunds update the actual resource_credits ledger once through existing canonical reconciliation. PayPal multiple captures preserve exact capture ownership and prior cumulative history. Original subscription refunds reopen exact subscription receivables; repayment refunds reopen the same underlying debt when appropriate. A refund of an excess repayment clears the exact operator refund liability without minting wallet credits or inventing a new fee. Processing fees, future reversals and original permanent subscription risks are not written off by this workflow.

operator_refunds and operator_refund_audit preserve the immutable original identity, quote, reason, actor, monotonic revisions and receipt digest. An active-order unique index plus BEGIN IMMEDIATE serializes preparations/claims locally. Every action uses an exact revision; every state change has an audit entry. Identity/audit mutation and unauthorized deletion are blocked by SQLite triggers. The audit cross-checks states, revisions, original context, receipt requirements and open/closed operation fences. Combined readiness exposes operator_refunds_pending or an unverifiable journal; no timer clears them. This is local SQLite ownership, not distributed multi-host fencing.

The single-dispatch tradeoff is deliberate: a crash after uncertainty commits but before any POST may leave an unknown outcome even if no refund occurred. No timeout can prove non-execution. An operator must obtain the exact provider refund ID and verify it; if the ID cannot be found/proven, the operation stays blocked and needs external merchant investigation. HTTP errors alone never authorize a second attempt or cancellation. There is no unknown-outcome reset endpoint. Prepared cancellation and a fresh quote are available only before dispatch. Merchant configuration changes are deliberately conservative: pending recovery requires the original configured merchant credentials/configuration fingerprint; restore those or investigate externally, never change target or resend. Full automatic account identity migration across key rotation is not implemented.
