## Implementation and trust boundaries

app/owner_payments.py merges owner-bound Stripe credit and PayPal credit/subscription/reversal orders with stable deterministic sorting, limit 1–50 (default 20), bounded offset and next-page indication. It returns only local ID, kind, amount, timestamps, status and permitted actions; no raw provider reference, request key, credential, merchant fingerprint or outbox internals. Its unresolved-credit hold scans across the entire owner inventory, independent of the selected page. The local history remains readable after eligibility loss and in NON_COMMERCIAL; NC exposes no payment actions. Empty history explicitly means no local rows on the page, not no external obligations.

GET /api/account/payments requires the actual signed-in owner. POST /api/account/payments/{provider}/{order_id}/verify requires owner authentication, the existing same-origin request-integrity header and exactly {"confirm":true}. It accepts no owner selector, reference binding, URL or observation. Expected ownership and a known local reference are checked before constructing the Stripe client and again inside the initial provider snapshot before actual I/O. Existing immutable owner/amount/reference/frozen-price and credential checks remain at final write, rejecting mid-flight changes. Owner-facing failures are generic 409 without provider evidence/secrets. The success marker means the readback completed; the refreshed local status may still be pending. 404, timeout, contradictory/unknown result and unknown creation never release a hold.

The service reuses the existing authenticated GET-only Stripe/PayPal canonical identity, settlement, refunds/disputes and economically empty terminal outcome verification. Every owner action is explicitly confirmed. It never creates a provider order, captures funds, retries creation, initiates a refund or binds an administrator-only missing reference. Missing references stay an operator investigation through the existing known-ID recovery workflow after independent provider identity validation. No heuristic automatic reference adoption was added.

Before new credit checkout admission, both provider schemas are initialized before BEGIN IMMEDIATE. Within that same write transaction a fresh request ID is blocked if either provider has an unresolved credit checkout for the owner, regardless of denomination. PayPal subscription fees likewise block a fresh order for the same original period. Existing exact idempotent known checkouts return their existing trusted URL; uncertain outbox retries remain blocked. Reversal targets retain their original pending-order guard. Paid/refunded/cancelled/failed local terminal records do not block unrelated new purchases; unknown statuses do. This relies on existing authoritative local terminal states, not browser cancellation. SQLite serializes this local database, not multiple independently stored hosts.

Resume URLs require HTTPS, an exact trusted Stripe/PayPal hostname, matching stored PayPal environment, no credentials, nonstandard port, control characters or backslash. Legacy invalid URLs cannot be exposed as resumable links or returned by exact checkout retry. New provider checkout responses use this same boundary, preserving an uncertain operation if validation fails. Shared owner_payments.js mounts on the actual account and credits pages, renders IT/EN with textContent, confirms resume/verification, paginates, clears sensitive controls on load/error and rejects late prior-language responses. No payment state is stored in browser storage. Credit shop removes legacy capture-based history controls, hides new purchases during a pending hold/NC and clears stale/error or prior-language controls. Direct /account/credits previously returned a JSON-encoded template; adding HTMLResponse fixes the actual route, enabling its scripts and localization. The browser tests check the real content type as well as behavior.
