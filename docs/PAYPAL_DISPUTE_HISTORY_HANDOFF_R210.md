## Functional contract now implemented

The existing owner **Verify status without collecting payment** and administrator **Reconcile from provider** actions now include authenticated dispute discovery for each exact capture of the selected known PayPal order. They still perform no financial POST/create/capture/refund. Stripe behavior and the separate explicit PayPal completion/refund dispatch contracts remain unchanged. If Disputes read permission is unavailable, the existing verification fails closed and records a private durable history gap; it never silently reports complete history.

app/paypal_dispute_history.py queries the fixed dispute collection by capture ID, with 50 entries/page and sequential pages. Only an exact original merchant HTTPS host, collection path, GET method, original capture filter, page size and next page are accepted from a continuation link. The returned link is never requested; the next query is rebuilt locally. Credentials, alternate ports, fragments, changed or duplicate query values, foreign paths/methods, unknown tokens, empty continuation, repeated disputes or malformed pages stop the scan. Deprecated token pagination is conservatively unsupported. Bounds: 50 pages per collection, 1000 unique disputes, 2000 capture/dispute references, 512 financial GET calls per dispute discovery. Existing refund discovery separately retains its bounds; OAuth token grants are not financial GET calls.

Each discovered dispute is read canonically, matched to the collection ID/status/time/amount and bound to known original captures. Every detail and full filtered collection, including empty collections, is read again; the original order is reread after discovery too. Any unstable or incomplete snapshot prevents settlement. The API-visible collections are bounded observations of this order, not a global merchant statement, proof of future stability or independent certification of provider retention/visibility.

A single-capture dispute can hold an exact partial EUR amount up to its capture gross. A multicapture dispute is supported only when every transaction identifies a distinct known capture, its gross equals the canonical capture gross, and the dispute total equals their complete gross sum. This gives an exact allocation without a proportional guess. Every referenced capture must return the dispute in its filtered collection. Foreign-order transactions, missing gross values, partial multicapture amounts and mismatched sums remain blocked. Existing single-capture hold identities are preserved; full multicapture holds have capture-specific identities. A changed allocation/amount cannot overwrite an original immutable hold.

Common open statuses hold funds. Ordinary seller-favour/buyer-cancellation results release; ordinary buyer-favour results retain permanent loss. Unknown outcomes, payout/protection results, nontrivial money/fund movements or unsupported partial refund amounts remain uncertain and pending; this implementation never guesses their actual money movements. The signed webhook path shares the same strict normalization for supported single-capture cases. Multicapture webhooks still require the complete explicit history workflow. Opposing terminal outcomes never release permanent loss or silently disappear; prior terminal-integrity guards remain intact.

## Atomic ledger and durable gaps

Normalized dispute risks enter the original fulfillment transaction alongside canonical funding and historical refunds. The final write rechecks immutable owner/order/amount/kind/period/provider/environment, exact current merchant configuration, original epoch/fence/outbox and existing refund/capture bindings. No provider I/O occurs under a database write lock. Refund and dispute exposure is capped by each actual capture's remaining gross, so first discovery never publishes spendable gross credit and overlap never debits the same money twice. Existing credits, original subscription risk and repayment allocation semantics are preserved. The repayment integration test proves that discovered risk reopens the exact old receivable and a supported release restores that allocation without minting wallet credits. Original permanent subscription-loss resolution remains open.

A failed/incomplete authenticated scan records an immutable **paypal_history_gap** event, bound to the unchanged original order and owner. It retains any dispute IDs actually observed before failure; those IDs must appear in a later complete valid scan before the gap can close. A later consistently empty result cannot erase a previously observed dispute. Repeated equivalent failures reuse an existing pending gap; a new failure after successful recovery creates a new event instead of reopening an immutable applied event. Unsafe original-context drift cannot bind a gap to the wrong owner/configuration. Financial readiness and the private owner history see the pending gap through their existing journal rules.

Successful full reconciliation closes matching gaps in the same transaction as actual financial settlement. Failures after funding roll back wallet, captures, risk and gap closure together. An ordinary unpaid capture-completion or webhook fulfillment cannot bypass a pending history gap. Already-paid capture readback remains idempotent and cannot clear the gap. A valid but locally conflicting dispute amount persists a private review gap and leaves the old hold unchanged. Previously recorded local disputes cannot vanish from a complete snapshot.

These are local SQLite invariants. No distributed coordinator, cross-host serializability or actual provider lifecycle acceptance is claimed.
