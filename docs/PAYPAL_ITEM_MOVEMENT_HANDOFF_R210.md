## Completed exact partial multicapture workflow

PayPal's canonical disputed-transaction items can supply read-only disputed amounts. New app/paypal_dispute_details.py validates these as exact allocation evidence. If any transaction includes an item collection, every transaction in that dispute must include one. Each collection has 1–100 entries and the combined proof at most1000. Every item needs a distinct bounded non-control identifier and positive exact EUR cents; identifiers are also unique across captures to reject ambiguous duplicated evidence. Optional quantity must be a positive whole-number string, but is never multiplied into the already-disputed monetary amount. Item names, descriptions, notes and buyer content are ignored.

The per-capture item sums must be positive, no larger than the original canonical capture gross, and together exactly equal the dispute total. A supplied transaction gross still must match the original capture. Capture membership, original owner/merchant/epoch, fence/outbox and repeated canonical detail/collection/order checks remain the prior authenticated history contract. No browser-supplied allocation or proportional estimate is accepted. Without item evidence, the previous exact full-gross allocation remains supported; partial multicapture without sufficient evidence stays blocked.

Only the proof method, item count and SHA256 of the canonical capture/item/cent tuples are retained with each immutable normalized risk event; no item identifiers or descriptions are added to owner/admin DTOs. Example:the original captures are3.00+2.00 EUR; the provider items allocate1.25+0.75 EUR to the first capture and1.00 EUR to the second. Exactly3.00 EUR is held, leaving 2.00 EUR in the commercial wallet. A quantity 99 on the 1.25 item does not multiply that amount. A supported seller-favour resolution restores the 5.00 EUR wallet; an ordinary buyer-favour outcome retains the exact 3.00 EUR loss. An original subscription records the exact 3.00 EUR risk without minting wallet credit; original permanent fee-loss resolution remains a separate open obligation.

These normalized risks use the existing single atomic funding/refund/risk transaction. First discovery cannot expose gross spendable credit, concurrent replay cannot duplicate adjustment, and unsupported/mismatched evidence leaves the existing durable history gap. Existing immutable hold identity and opposing-terminal-result guards remain intact. An amount change cannot rewrite an already bound original hold. Actual /account and /account/credits IT/EN390/1280 pages traverse verification, exact held amount, private history and supported release through real local API/SQLite. No financial provider mutation occurs through verification.

## Completed private movement-observation workflow

For uncertain payout cases or supplied current/legacy movement arrays, the canonical event now retains a bounded safe review DTO with an evidence digest. Each array has at most50 records. Recognized party, direction, reason, EUR cents and initiation time become observations; missing/unknown fields become explicit unknown/unavailable values and fixed warning codes. Malformed arrays, malformed/non-EUR money and false-valued invalid fields cannot masquerade as absent evidence or authorize a seller release. Cryptocurrency is explicitly unsupported. Both arrays may describe the same transfer:they are shown separately and never added as independent cash.

No source field or inferred sum is settlement authority. **settlement_proven is always false.** A CREDIT, a fee reimbursement, a buyer payment or an initiated movement cannot release a hold, create a receivable settlement, mint customer credit or charge a processor fee to the customer. Payout/protection/money-movement cases remain uncertain and pending under the prior financial guards. A later separately supported canonical dispute result may resolve the risk; the old observations remain immutable audit history, not retrospectively marked as completed transfers.

Administrator payment-ledger readback adds movement_reviews only for the selected page's PayPal positions. It scans at most200 events plus one truncation marker, returns at most20 distinct evidence snapshots per order, and deduplicates the same snapshot across captures. It revalidates safe DTOs on read. Corruption produces generic409 rather than leaking content or rendering arbitrary fields. Original private normalized journals remain the detailed history; truncated views explicitly say so. The owner endpoint still returns only its permitted local payment fields, aggregate held amount and pending boolean. Provider movement details, fee observations, item/customer text and evidence references are not exposed to owners.

The shipped administrator panel renders a named focusable scrolling table of party, direction, reason, EUR amount, initiation and source, with a clear statement that initiation does not prove completion. It offers no settlement or funds-release action. Rendering uses textContent. Financial refresh failures clear stale observations; explicit retry reloads the actual journal. Shared template cache keys were updated. Owner templates/controls remain the completed previous workflow.

Amounts include exact decimal cent strings as well as API integers; the renderer uses BigInt for grouping and fractions. Four actual-browser IT/EN cases demonstrate 90071992547409.93 EUR without JavaScript rounding. This is diagnostic precision only:the observed amount never enters the customer's wallet or fee ledger. The tests deliberately show this very large CREDIT fee observation while the wallet remains 2.00 EUR and the 3.00 EUR dispute stays pending.

## Concrete settlement proof blocker and independent work

Current dispute movement contracts describe initiation, party, direction and amount, but do not supply a uniquely bound completed transaction identifier. Reporting transaction status/T-codes alone are not a verified unique binding to a particular case; free-text subjects/notes are not proof. Therefore no automatic payout/protection release was implemented from these fields. This is a missing evidence/attribution contract, not an invitation to weaken the gate or merely label unknown money as settled. Actual isolated merchant statements/receipts with authoritative case/capture/completed-transaction binding and conservation proof are needed for the next settlement protocol. Real sandbox validation remains unavailable too.

Independent exact item allocation and private operator review were completed while that proof remained blocked. Remaining A4/A5 work includes unallocated or ambiguous item histories, global merchant historical completeness, actual payout/protection/fund-movement proof and settlement, legacy unknown orders/obligations and original permanent subscription fee loss. The new diagnostic table is not financial completion or a complete merchant statement. No raw reporting query was added that could mistake a similar amount/date/reference or provisional reversal for this dispute's final settlement.
